# R016: Continuous Improvement Rules

When a user points out a rule violation, the relevant rule MUST be updated immediately — before continuing the original task.

## Overview

Rule violations reveal gaps or ambiguities in the rules themselves. Instead of just acknowledging the violation, the agent must update the rule to prevent recurrence, commit the change, and then resume the original task. Deferred fixes compound into patterns.

## Priority

**MUST** — Non-negotiable timing: rule update happens NOW, not later. "I'll fix it later" is itself a violation.

## Key Requirements

**Workflow:**
1. Acknowledge violation
2. Identify root cause (which rule was weak/unclear?)
3. Update the rule (add clarity, examples, self-checks)
4. **Rule Wiring Check** — confirm the rule text is actually wired into an execution path (see below); do not skip to commit on text-only edits
5. Commit the change
6. Continue original task following updated rules

**Defect response matrix:**

| Defect Type | Rule Update | Memory | Issue | Skill Promotion |
|-------------|:-----------:|:------:|:-----:|:---------------:|
| Rule violation (agent behavior) | ✅ | — | — | — |
| CI/infra defect | — | ✅ | ✅ | — |
| Process gap (workflow hole) | ✅ | ✅ | ✅ | ⚠️ (3회+ 반복 시) |
| Repeatable system bug | — | ✅ | ✅ | ⚠️ (구조적일 경우) |
| Agent selection failure | — | ✅ | — | ✅ (라우팅 스킬 업데이트) |
| External repo convention miss | ✅ | ✅ | — | ⚠️ (3회+ 반복 시) |

**Skill Promotion threshold (clarified, #1268):** candidacy for skill-extraction begins at **≥2 occurrences** of the same feedback-memory pattern (proposes a candidate via `skill-extractor`'s 4-criteria gate, Phase 1); confirmed promotion to a tracked "failure pattern" and actual skill creation requires **≥3 occurrences**. The two-tier threshold prevents both premature extraction (1 occurrence = noise) and indefinite deferral.

**Auto-register directive (session 102 / #1238):**

Genuine defects and process gaps surfaced during release workflows (e.g., `post-release-followup` skill) MUST be auto-registered as GitHub issues without user confirmation. This applies to defects that clearly belong in the Issue column of the matrix (CI/infra defect, process gap, repeatable system bug). Only code-changing "immediate action" items require user confirmation before proceeding. Cross-referenced in the `post-release-followup` skill's "Auto-Register Genuine Defects (no-ask)" section.

**Adaptive Harness Integration:** when repeating agent failures or suboptimal routing is detected, record a feedback memory immediately, then run `/omcustom:adaptive-harness --learn` to fold the failure pattern into the project profile — connecting R016's promotion loop to the adaptive-harness skill's cross-session learning.

**Anti-patterns to avoid:**
- "I'll update the rule later"
- "This is a one-time exception"
- "Let me finish the task first"
- "Calibration/humility during action-oriented tone" (auto mode, "ㄱㄱ") — defer self-questioning to post-task feedback memory instead of stalling on an action-mode signal

## Rule Wiring Check (#1533)

Adding rule text and wiring that text into an actual execution path (a workflow YAML step, a skill's invocation logic, a script, CI configuration) are **separate acts**. A promotion that only edits the rule file — without confirming or adding the corresponding execution-path hookup — is incomplete, even though the text itself is correct.

**Judgment items (Workflow step 4, between "Update the rule" and "Commit"):**

1. Is there an execution path where this rule clause is meant to fire (e.g., an `auto-dev.yaml` step, a hook, a CI check)?
2. If yes, has it actually been wired in — not just described in prose?
3. If there is no applicable execution path for this clause (pure prompt-based guidance with no automation surface), state **"wiring not required"** explicitly rather than leaving the question unaddressed.

**Rule:** if wiring is required but only the rule text was added, the promotion is NOT complete — treat it the same as an unverified `[Done]` declaration ([[r020]] Core Rule: "actual outcome ≠ attempt").

**Origin (#1533):** v1.1.35 added an R017 (b) clause but never wired a corresponding trigger point into `auto-dev.yaml` — `mgr-sauron` caught the gap with a `[FAIL]` block during structural verification, and the release only passed after the missing wiring was added. The rule text alone had looked complete; only checking the execution path surfaced the gap.

Cross-reference: [[r017]] (mgr-sauron structural verification catches unwired clauses), [[r020]] (actual outcome ≠ attempt, applied to rule promotions themselves).

## Rule Clause Retirement (#1473)

R016's promotion loop (violation → new clause) drives **monotonic corpus growth** — session context pays a fixed injection cost (~49.5k tokens) for every rule file, so an unbounded corpus is a real budget problem, not just a maintenance one. Retirement introduces a symmetric counter-loop: the promotion loop stays (its benefit is proven) while a matching retirement loop caps corpus size at a steady state instead of removing accumulated value.

**Retirement candidates:**

| Candidate | Criterion |
|-----------|-----------|
| Fixed platform-bug narrative | The underlying CC bug is already patched, so the workaround clause has no remaining behavioral value |
| Long-dormant clause | Not invoked by a violation citation or `/homework` retrospective across 2 minor releases |

**Procedure:** (1) track invocations lightly via feedback memory during retrospectives — no full automation needed; (2) a clause dormant for 2 minor releases + no remaining behavioral value becomes a retirement candidate; (3) wrap it in `<!-- RETIRED (release vX.Y.Z, N releases dormant): original text -->` so it drops out of auto-injection but stays Read-able (lossless, reuses the [[r005]] HTML-comment pattern); (4) if the same pattern recurs, uncomment it — restoration mirrors promotion exactly.

**Version-note retention policy:** CC version notes (`> **v2.1.NNN+**:`) inside rules stay visible for only the most recent 2-3 minor releases; older ones are HTML-commented or moved to `guides/claude-code/15-version-compatibility.md`. [[r023]]'s Deprecated-Platform-Feature Staleness Check deterministically flags retirement candidates early. The current baseline is **v2.1.212+ visible**.

### Raising the Baseline = Sweeping Every Rule File, in the Same Release (#1563)

Raising the retention baseline obligates a **full sweep of all 23 rule files within that same release**, HTML-commenting every note below the new line. Raising the line and deferring the application leaves the corpus inconsistent with its own stated baseline — and that inconsistency is invisible until a later retrospective rediscovers it as "N notes still visible" debt. The sweep covers both `.claude/rules/**` and `templates/.claude/rules/**`, and residual counting must **distinguish inside-comment from outside-comment**: a plain `grep` also counts already-retired notes inside comments and skews the verdict.

| Anti-pattern | Required |
|--------------|----------|
| Raise the baseline and defer the sweep of existing notes to a later release | Complete the baseline raise and the full rule-file sweep in the same release |
| Judge residuals by `grep -c` hit count | Count only **visible** residuals, separating inside-comment from outside-comment |

Origin: #1563 찐빠 #4 — R016 declared a v2.1.212 baseline, yet three visible v2.1.208 notes survived in R001/R005/R012 and were only retired later, in v1.1.44. Cross-ref: [[r005]] (HTML-comment context optimization), [[r017]] (Count Sync — exhaustive grep plus meaning-level adjudication).

## External Repo Contribution Pre-Check (v0.147.0)

Before starting work on contributing to an external repository (skill submission, agent contribution, plugin development), MUST read these files in the target repo FIRST round:

| File | Purpose |
|------|---------|
| `CONTRIBUTING.md` | Submission rules, PR conventions |
| `AGENTS.md` | Agent contribution guide (if applicable) |
| `docs/adding-a-*.md` | Domain-specific add guide |
| `package.json` scripts | Validation commands (e.g., `npm run ci`) |

**Self-check before first implementation commit:**
- [ ] Read CONTRIBUTING / AGENTS / skill-checklist
- [ ] Identified frontmatter convention + metadata enums
- [ ] Identified validation commands
- [ ] Confirmed domain fit

Reference issues: #1188 item #5, #1188 item #7, #1198 item #5.
