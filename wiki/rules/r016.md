# R016: Continuous Improvement Rules

When a user points out a rule violation, the relevant rule MUST be updated immediately — before continuing the original task.

## Overview

Rule violations reveal gaps or ambiguities in the rules themselves. Instead of just acknowledging the violation, the agent must update the rule to prevent recurrence, commit the change, and then resume the original task. Deferred fixes compound into patterns.

## Priority

**MUST** — Non-negotiable timing: rule update happens NOW, not later. "I'll fix it later" is itself a violation.

## Key Requirements

**Workflow:**
1. Acknowledge violation
2. Identify root cause (which rule was weak/unclear?)
3. Update the rule (add clarity, examples, self-checks)
4. **Rule Wiring Check** — confirm the rule text is actually wired into an execution path (see below); do not skip to commit on text-only edits
5. Commit the change
6. Continue original task following updated rules

**Defect response matrix:**

| Defect Type | Rule Update | Memory | Issue | Skill Promotion |
|-------------|:-----------:|:------:|:-----:|:---------------:|
| Rule violation (agent behavior) | ✅ | — | — | — |
| CI/infra defect | — | ✅ | ✅ | — |
| Process gap (workflow hole) | ✅ | ✅ | ✅ | ⚠️ (3회+ 반복 시) |
| Repeatable system bug | — | ✅ | ✅ | ⚠️ (구조적일 경우) |
| Agent selection failure | — | ✅ | — | ✅ (라우팅 스킬 업데이트) |
| External repo convention miss | ✅ | ✅ | — | ⚠️ (3회+ 반복 시) |

**Skill Promotion threshold (clarified, #1268):** candidacy for skill-extraction begins at **≥2 occurrences** of the same feedback-memory pattern (proposes a candidate via `skill-extractor`'s 4-criteria gate, Phase 1); confirmed promotion to a tracked "failure pattern" and actual skill creation requires **≥3 occurrences**. The two-tier threshold prevents both premature extraction (1 occurrence = noise) and indefinite deferral.

**Auto-register directive (session 102 / #1238):**

Genuine defects and process gaps surfaced during release workflows (e.g., `post-release-followup` skill) MUST be auto-registered as GitHub issues without user confirmation. This applies to defects that clearly belong in the Issue column of the matrix (CI/infra defect, process gap, repeatable system bug). Only code-changing "immediate action" items require user confirmation before proceeding. Cross-referenced in the `post-release-followup` skill's "Auto-Register Genuine Defects (no-ask)" section.

**Adaptive Harness Integration:** when repeating agent failures or suboptimal routing is detected, record a feedback memory immediately, then run `/omcustom:adaptive-harness --learn` to fold the failure pattern into the project profile — connecting R016's promotion loop to the adaptive-harness skill's cross-session learning.

**Anti-patterns to avoid:**
- "I'll update the rule later"
- "This is a one-time exception"
- "Let me finish the task first"
- "Calibration/humility during action-oriented tone" (auto mode, "ㄱㄱ") — defer self-questioning to post-task feedback memory instead of stalling on an action-mode signal

## Rule Wiring Check (#1533)

Adding rule text and wiring that text into an actual execution path (a workflow YAML step, a skill's invocation logic, a script, CI configuration) are **separate acts**. A promotion that only edits the rule file — without confirming or adding the corresponding execution-path hookup — is incomplete, even though the text itself is correct.

**Judgment items (Workflow step 4, between "Update the rule" and "Commit"):**

1. Is there an execution path where this rule clause is meant to fire (e.g., an `auto-dev.yaml` step, a hook, a CI check)?
2. If yes, has it actually been wired in — not just described in prose?
3. If there is no applicable execution path for this clause (pure prompt-based guidance with no automation surface), state **"wiring not required"** explicitly rather than leaving the question unaddressed.

**Rule:** if wiring is required but only the rule text was added, the promotion is NOT complete — treat it the same as an unverified `[Done]` declaration ([[r020]] Core Rule: "actual outcome ≠ attempt").

**Origin (#1533):** v1.1.35 added an R017 (b) clause but never wired a corresponding trigger point into `auto-dev.yaml` — `mgr-sauron` caught the gap with a `[FAIL]` block during structural verification, and the release only passed after the missing wiring was added. The rule text alone had looked complete; only checking the execution path surfaced the gap.

Cross-reference: [[r017]] (mgr-sauron structural verification catches unwired clauses), [[r020]] (actual outcome ≠ attempt, applied to rule promotions themselves).

## Rule Clause Retirement (#1473)

R016's promotion loop (violation → new clause) drives **monotonic corpus growth** — session context pays a fixed injection cost (~49.5k tokens) for every rule file, so an unbounded corpus is a real budget problem, not just a maintenance one. Retirement introduces a symmetric counter-loop: the promotion loop stays (its benefit is proven) while a matching retirement loop caps corpus size at a steady state instead of removing accumulated value.

**Retirement candidates:**

| Candidate | Criterion |
|-----------|-----------|
| Fixed platform-bug narrative | The underlying CC bug is already patched, so the workaround clause has no remaining behavioral value |
| Long-dormant clause | Not invoked by a violation citation or `/homework` retrospective across 2 minor releases |

**Procedure:** (1) track invocations lightly via feedback memory during retrospectives — no full automation needed; (2) a clause dormant for 2 minor releases + no remaining behavioral value becomes a retirement candidate; (3) wrap it in `<!-- RETIRED (release vX.Y.Z, <reason>): original text -->` so it drops out of auto-injection but stays Read-able (lossless, reuses the [[r005]] HTML-comment pattern); (4) if the same pattern recurs, uncomment it — restoration mirrors promotion exactly.

The `<reason>` slot is not free-form: it maps one-to-one onto the two candidate categories above. A long-dormant clause records `N releases dormant`; a fixed-platform-bug narrative records `retention baseline below v2.1.NNN`. Keeping the marker aligned with the category makes the retirement corpus greppable by *why* a clause left, which is what lets a later baseline sweep separate genuinely dormant clauses from version-note pruning.

**Version-note retention policy:** CC version notes (`> **v2.1.NNN+**:`) inside rules stay visible for only the most recent 2-3 minor releases; older ones are HTML-commented or moved to `guides/claude-code/15-version-compatibility.md`. [[r023]]'s Deprecated-Platform-Feature Staleness Check deterministically flags retirement candidates early. The current baseline is **v2.1.230+ visible** (raised from v2.1.212, v1.1.50).

**The baseline is a relative width, not a fixed constant:** when v2.1.212 was set, latest CC was v2.1.233 — a ~21-patch retention width. To preserve that same width at this raise (v1.1.50; `claude --version`/`npm view` measured v2.1.251), the baseline must be v2.1.230. Future baseline raises should recompute as "latest measured − ~20 patches," not restate a fixed number.

### Retirement Adjudication Criteria — Below-Baseline ≠ Automatic Retirement

Falling below the retention baseline only defines the **review pool** for retirement — it does not by itself decide **whether** a note retires. A sub-baseline note is only retired (wrapped in an HTML comment) when it satisfies **all three** of the following conditions; if even one fails, the note is **kept**, and the keep verdict plus its reason is recorded in the sweep log.

| Condition | Question |
|-----------|----------|
| (a) No citation | Is the note NOT cited by any other visible note as "the same family" (cf., an extension of, adjacent to, etc.)? |
| (b) Non-current | Does the note NOT describe current behavior (e.g., it narrates a past state that has since been rolled back or re-patched)? |
| (c) No diagnostic value left | Is there no remaining retrospective diagnostic value (a reason to reinterpret past observations through it)? |

All three true → retire. Any one false → keep (a note cited as an anchor by another visible note, or one that still describes current behavior, or one that still carries diagnostic value, is worth preserving even below the baseline). This criterion was reverse-derived from the actual adjudications made across the 4 parallel groups in v1.1.50 — reading "below baseline = immediate retirement" literally contradicts it.

### Raising the Baseline = Sweeping Every Rule File, in the Same Release (#1563)

Raising the retention baseline obligates a **full sweep of all 23 rule files within that same release** — "sweep" does not mean HTML-commenting every sub-baseline note wholesale, it means **full adjudication** under the three-condition test above (retire or keep each note, and record the reason when kept). Raising the line and deferring the review itself leaves the corpus inconsistent with its own stated baseline — and that inconsistency is invisible until a later retrospective rediscovers it as "N notes still visible" debt. The no-deferral rule is unchanged; what changes is that the obligation is "full adjudication," not "full retirement." The sweep covers both `.claude/rules/**` and `templates/.claude/rules/**`, and residual counting must **distinguish inside-comment from outside-comment**: a plain `grep` also counts already-retired notes inside comments and skews the verdict.

| Anti-pattern | Required |
|--------------|----------|
| Raise the baseline and defer the review of existing notes to a later release | Complete the baseline raise and the full-rule-file **adjudication** (retire/keep + record the keep reason) in the same release |
| HTML-comment every sub-baseline note wholesale, without adjudication | Apply the three-condition retirement test (no citation AND non-current AND no diagnostic value left) to each note individually |
| Judge residuals by `grep -c` hit count | Count only **visible** residuals, separating inside-comment from outside-comment — residuals by themselves are not a defect (they can be the correct outcome of a keep verdict) |

Origin: #1563 찐빠 #4 — R016 declared a v2.1.212 baseline, yet three visible v2.1.208 notes survived in R001/R005/R012 and were only retired later, in v1.1.44. Cross-ref: [[r005]] (HTML-comment context optimization), [[r017]] (Count Sync — exhaustive grep plus meaning-level adjudication).

**Sweep results (v1.1.50):** raising the baseline v2.1.212→v2.1.230 split rule-file ownership across 4 parallel groups, each sweeping only its own assigned files — ownership split by **file**, not by task type ("retirement duty" vs "new-note duty"), so parallel agents never edited the same file concurrently (a corpus-level self-application of R009's file-disjoint principle). Outcome: **2 retired, most kept**. The 2 retired clauses were pure historical narratives citing no still-visible note (R006's v2.1.201 Sonnet-5-harness-reminder-delivery note and v2.1.204 headless-SessionStart-streaming note) — a direct positive instance of the "cited by no visible note" criterion, i.e. the two retirements happened precisely because condition (a) held while, for the kept notes, at least one condition failed (an anchor another visible note cites as "the same family," e.g. v2.1.222 citing v2.1.211/212/214, or a note that still described current behavior). This means the adjudication ran on citation relationships, not the version number alone, and **this citation-based criterion was promoted to a formal rule clause in this same release** (see Retirement Adjudication Criteria above) — not deferred as a future review item — because mgr-sauron's [[r017]] structural verification flagged the gap as a `[FAIL]` and required same-commit reconciliation before the release could pass. The residual **49 notes across 11 files** are therefore not a defect: they are the correct outcome of the three-condition adjudication (kept), and future retrospectives should not misread this residual count as unaddressed debt.

## External Repo Contribution Pre-Check (v0.147.0)

Before starting work on contributing to an external repository (skill submission, agent contribution, plugin development), MUST read these files in the target repo FIRST round:

| File | Purpose |
|------|---------|
| `CONTRIBUTING.md` | Submission rules, PR conventions |
| `AGENTS.md` | Agent contribution guide (if applicable) |
| `docs/adding-a-*.md` | Domain-specific add guide |
| `package.json` scripts | Validation commands (e.g., `npm run ci`) |

**Self-check before first implementation commit:**
- [ ] Read CONTRIBUTING / AGENTS / skill-checklist
- [ ] Identified frontmatter convention + metadata enums
- [ ] Identified validation commands
- [ ] Confirmed domain fit
