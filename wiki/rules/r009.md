# R009: Parallel Execution Rules

Two or more independent tasks MUST execute in parallel. Sequential execution of parallelizable tasks is a violation.

## Overview

Parallel execution maximizes throughput and reduces wall-clock time. Before spawning 2+ parallel agents, the Agent Teams eligibility check ([[r018]]) must be performed — Agent Teams may be required instead of raw Agent tool calls. Adaptive splitting handles stalled agents at runtime.

## Priority

**MUST** — Enforced. Sequential execution of independent tasks requires correction. PostCompact hook re-injects this rule.

## Key Requirements

**Independence criteria (MUST parallelize):**
- No shared mutable state between tasks
- No sequential dependencies
- Each completes independently

**File-disjoint ≠ independent for local git state (#1518):** Local git-state-changing operations (`checkout`/`pull`/branch create-delete-rename/`commit`/`stash`/`merge`/`rebase`) contend on a single process-level shared mutable state — the working tree, branch pointer, index, and HEAD — even when the edited files are disjoint. Serialize: only ONE git-state-changing agent runs at a time; finish the git step sequentially, then parallelize the rest. Read-only queries (`git status`/`log`/`diff`, `gh` reads) remain parallelizable — only state changes are restricted.

| Anti-pattern | Required |
|--------------|----------|
| Spawn 2+ git-state-changing agents in parallel because their edited files are disjoint | Serialize git-state changes to one concurrent agent; parallelize the rest after it completes |

Origin: #1518 (a working branch went stale from two git agents running close together despite disjoint edited files).

**File-disjoint ≠ resource-disjoint (#1598):** Beyond git state, parallel agents contend over three more shared resources — **the repo files a verification command touches, the CPU, and `$TMPDIR`**. Disjoint edit targets guarantee none of them.

| Resource | Parallel-safe only when |
|----------|------------------------|
| Verification command (`bun test`, etc.) | The suite never moves/deletes/restores repo-tracked files and does not depend on second-scale timeout budgets. Otherwise the orchestrator reclaims it and runs it **once, serially** |
| CPU | Tests with second-scale timeout budgets are never run concurrently — under saturation, process startup alone can exceed the budget |
| `$TMPDIR` | Each agent uses its own unique subpath. Sharing a fixed path makes measurements like "N leaked files" count a sibling's residue |

**Tests must not move tracked files:** a `cp` → `rm` → `finally`-restore pattern causes more than parallel-contention false positives — if the process is interrupted, the tracked file simply stays gone. Copy fixtures into a unique temp directory and manipulate the copy; treat the original as read-only.

| Anti-pattern | Required |
|--------------|----------|
| Put the same `bun test` in every agent's completion criteria because the edit targets are disjoint | Reclaim verification to a single serial run, or disclose the sharing and rule out sibling contention first when interpreting results |
| A test `cp`→`rm`→`finally`-restores a real repo-tracked file | Copy into a unique temp directory and manipulate the copy — original stays read-only |

Origin: #1598. Cross-ref: [[r010]] (Parallel Delegation — Sibling-Agent Disclosure: what the brief must disclose), [[r023]] (Delegated Verification Floor).

**Agent Teams gate:** Quick rule — 3+ agents OR review cycle OR 2+ issues in same batch → use Agent Teams ([[r018]]).

**Execution limits:**

| Rule | Detail |
|------|--------|
| Max instances | 5 concurrent (soft default: 4) |
| Large tasks (>3 min) | MUST split into parallel sub-tasks |
| Orchestrator | Must stay singleton, never parallelized |

**Per-session 200-subagent spawn cap removed (v2.1.224+):** long-running sessions no longer refuse new agents once a cumulative spawn total is reached. What was removed is the **session-cumulative total**, not the concurrency limit — the "Max instances: 5 concurrent" row above is a *concurrency* constraint and remains fully in force, as does the nested-spawn depth limit. Practical consequence: a late-iteration spawn failure inside a long autonomous loop (`/fsd`) must no longer be diagnosed as cap exhaustion; look for the real cause instead.

**Subagent forking on by default — "isolated context" no longer universal (v2.1.232+):** Subagent forking is now enabled by default, so a `subagent_type: "fork"` subagent inherits the **full conversation and prompt cache**. The "Instance independence — Isolated context, no shared state" row in the execution-limits table above **does not hold for forks**: a fork is a *context copy*, not an isolated parallel instance. Do not treat forks as ordinary subagents when designing a parallel batch around the independence criteria at the top of this section — the orchestrator's context carries over, so the delegation prompt's scope statement is no longer the only boundary. On older CC this inheritance was an opt-in exception path. The same release made **non-teammate agent spawns in interactive sessions run in the background by default**, so a spawn return is not a completion signal ([[r010]], [[r020]]).

**Workflow fan-out prefix stagger + container core count (v2.1.229+):** Workflow fan-out now **staggers** sibling agents that share a prompt prefix so later siblings reuse the prefix cache (disable with `CLAUDE_CODE_WORKFLOW_PREFIX_STAGGER_MS=0`). A same-prefix parallel batch is therefore an *intentionally time-shifted* dispatch, not a simultaneous one — do not read the delayed start of some agents as a stall signal for Adaptive parallel splitting below. On older CC each sibling paid the prefix cost separately. Also fixed: dynamic workflows used the **host** core count inside CPU-limited containers, so effective concurrency in a container may be lower than the caps in the table above.

**Fable 5 long-lived subagent reuse (#1435):** Fable 5는 long-lived subagent 재사용(단일 subagent가 여러 단계를 이어서 수행)에 강함 — 현행 R009 병렬 실행 원칙과 상충하지 않으며, Fable 5 실행 시 short-lived 병렬 다수 대신 long-lived 재사용도 유효한 선택지. 상세는 `guides/claude-code/16-fable5-prompting.md`.

**Adaptive parallel splitting:** When an agent takes 2x+ longer than peers, spawn independent follow-up tasks immediately without canceling the stalled agent.

**Announce-execution consistency (Self-Check #6):** All tool calls announced in prose MUST be dispatched in the SAME message as the announcement — a tool that "runs next turn" instead is a violation. The check is now a **pre-dispatch count match**: the number N of tools stated in the announcement prose MUST equal the number of `tool_use` blocks actually included in that same message. The drop direction is random — sometimes the verify Bash slips (v1.1.22/23), sometimes the action delegate slips (v1.1.27 session) — so direction-specific wording proved insufficient after 3 recurrences; the count-match check is the only verified mitigation (#1512, #1503).

**LLM Batch Output Token Budget:** The symmetric output-side counterpart to the input-side giant-prompt heuristic above. When one LLM call scores/classifies/extracts structured output (e.g. JSON) for N items, pre-compute `output_budget = N × per-item output tokens` BEFORE the call — exceeding `max_tokens` truncates mid-structure and causes a silent parse failure (the call "succeeds" but JSON.parse throws). Fix: chunk into ≤40-item batches and constrain per-item output length; raising `max_tokens` alone only defers the failure as the list grows (#1320, #1321).

**Display format:**
```
[1] mgr-creator:sonnet → Create Go agent
[2] lang-python-expert:sonnet → Review Python code
```

**Narrative announcement format — advisor-regex parity (#1595 #5):** A prose parallel-dispatch announcement uses the **literal form with a bracketed number at the start of the line**. Never prefix it with a markdown list marker or a backtick — the R008 detection regex requires the bracketed number at line start, so the list form makes a **rule-compliant response count as a violation**.

```
[secretary][opus] → Spawning:
[1] mgr-updater:sonnet → Group A rule-file update
[2] lang-typescript-expert:sonnet → Group B test hardening
```

| Anti-pattern | Required |
|--------------|----------|
| List marker or backtick before the number | Bracketed number at line start — nothing but whitespace before it |
| Header without the colon | A colon after Spawning is required |
| Agent-type/model followed by a description with no arrow | An arrow after agent-type:model is required |

The arrow is recognized in exactly three forms: U+2192, the ASCII hyphen-greater pair, and the U+2014-greater pair. This form is identical to the Display format block above — the two must never demand different shapes. Where the rule wording and the detector regex diverge, **compliant responses are counted as violations and that count then becomes the argument for changing the rule again**; change the advisor regex in the same commit as any format change ([[r016]] Rule Wiring Check). Full literal reference: [[r008]] 「Spawn Announce 리터럴」.

**Result aggregation:**
```
[Summary] {succeeded}/{total} tasks completed
  ✓ agent-1: success
  ✗ agent-2: failed (reason)
```

## Anti-Pattern: Single Agent Giant Prompt

단일 에이전트에 5000+ 토큰 multi-domain 프롬프트를 위임하는 것은 R009 위반이다. 이 패턴은 latency timeout, user cancellation, review loop 불가능을 유발한다.

**토큰 임계치 가이드 (#1085):**

| 조건 | 권장 |
|------|------|
| < 5000 tokens, single domain | 단일 에이전트 가능 |
| ≥ 5000 tokens 또는 3+ domains | 도메인별 분할 + 병렬 에이전트 (R009) |
| ≥ 8000 tokens 또는 4+ domains | Agent Teams 사용 필수 ([[r018]]) |

```
❌ WRONG: Single agent receives massive multi-domain prompt (>5000 tokens)
   Agent(arch-documenter, prompt: <9000-token M2 plan across 7 areas>)
✓ CORRECT: Pre-decompose by domain, spawn parallel agents per area
```

## Parallel Feature Integration Gate

Per-subagent "build green" does NOT guarantee integrated runtime correctness. When parallel feature subagents edit interdependent code (shared singletons, navigation stacks, API contracts), the orchestrator MUST run a combined build PLUS a runtime/smoke check (or device test for apps) after the parallel work merges — before declaring done.

> Origin: #1335 ③ — parallel lang-kotlin-expert rounds each reported "build green", but the combined runtime had a DataStore singleton crash, a Settings→Dashboard nav crash, a recording 400, and cursor pre-advance bugs — caught only by on-device testing.

| Anti-pattern | Required |
|--------------|----------|
| Trust each subagent's "build green" and declare done | Orchestrator runs a combined build + runtime/smoke gate on the merged result first |

Cross-reference: [[r020]] (actual outcome ≠ attempt; completion verification).
