# R011: Memory Integration Rules

Defines when and how agents persist knowledge across sessions using native auto-memory.

> This project uses **native auto-memory ONLY** (MEMORY.md + agent frontmatter `memory:`). The claude-mem and agentmemory MCP servers are NOT used — they were permanently removed (#1253).

## Overview

Native auto-memory (agent frontmatter `memory` field) is the sole persistence mechanism — it loads the first 200 lines of MEMORY.md into the system prompt. Default paths are overridable via the `autoMemoryDirectory` setting (v2.1.74+). There are no external MCP memory backends. Memory failures must never block the main task.

## Priority

**SHOULD** — Strong recommendation. Missing memory integration reduces cross-session effectiveness but does not block operations.

## Key Requirements

**Architecture:** Native auto-memory is the single backend. No external MCP dependencies.

**Memory scope:**

| Scope | Location | Git Tracked |
|-------|----------|-------------|
| `user` | `~/.claude/agent-memory/<name>/` | No |
| `project` | `.claude/agent-memory/<name>/` | Yes |
| `local` | `.claude/agent-memory-local/<name>/` | No |

**Session-end auto-save responsibility:**

| Action | Owner |
|--------|-------|
| Session summary + native MEMORY.md update | `sys-memory-keeper` |

**Best practices:**
- Consult memory before starting work; update it after discovering new patterns
- Keep MEMORY.md under 200 lines
- Do not store secrets or duplicate CLAUDE.md content
- Memory write failures are non-blocking

## Subagent memory:project Source-Tree Pollution Guard

> Origin: #1335 ② — a `lang-kotlin-expert` with `memory: project`, working in a Kotlin source subdirectory, wrote memory to `mobile/.../com/baekenough/secondbrain/.claude/agent-memory/` — inside the source package. Caught and removed just before commit.

A subagent with `memory: project` that runs in a **subdirectory** can create `.claude/agent-memory/` relative to its cwd, polluting the source tree (e.g., inside a source package directory). Memory must resolve to the **project root** `.claude/`, never a nested working directory.

| Anti-pattern | Required |
|--------------|----------|
| Accept a subagent's `.claude/agent-memory/` written under a source package | Verify memory writes land at project-root `.claude/`; remove any nested `.claude/agent-memory/` before commit |

**Pre-commit check:** Before committing subagent work, scan for stray nested memory directories:

```bash
find . -path '*/src/*/.claude' -o -path '*/main/*/.claude'
```

## Attention-Weight Memory Tiering

> Origin: #1279 (Dual-Brain scout:internalize partial internalization)

Memory entries are managed on two orthogonal axes: confidence (verification level, see Confidence Lifecycle) and **attention weight** (access frequency/recency). Four tiers apply: **Hot** (2+ references this session — top of MEMORY.md), **Warm** (referenced within the last 3 sessions — below Hot), **Cold** (3+ sessions unreferenced but still valuable — moved to `sessions_archive_*.md` with an index line only), **Archived** (90+ days unreferenced per Temporal Decay — index-only). Access promotes a tier immediately (Cold → Warm → Hot); non-access demotes it at session end (Hot → Warm after 1 session, Warm → Cold after 3, Cold → Archived once Temporal Decay's 90-day threshold is also met). `[permanent]`-tagged entries are exempt from both decay and demotion. `sys-memory-keeper` re-scans at session start (archive-eligibility) and session end (demotion + archive move), keeping the 200-line budget resident to Hot/Warm content while Cold/Archived stay index-only.

## Mid-Session Immediate Save

Save memory IMMEDIATELY upon surprising discovery — do not defer to session end.

| Trigger | Action | Rationale |
|---------|--------|-----------|
| Repeated pattern observed (2nd time) | Save `feedback_*.md` now | Pattern will recur within session |
| Unexpected tool behavior / workaround | Save `feedback_*.md` now | Session state defense |
| Subagent false-positive detected | Save `feedback_*.md` now | Prevent repeat in same session |
| User correction / feedback | Save `feedback_*.md` now | Honor correction immediately |

**Why Immediate (not session-end):** Session-end saves lose context: by the time the session ends, multiple discoveries have compounded and nuance is lost. Immediate saves preserve the exact trigger context that makes the memory actionable.

**Anti-pattern**: "I'll batch all learnings at session end" — by then you'll have forgotten WHY each one mattered, and further violations may have occurred using the un-saved pattern.

## Procedure-Summary Scope Tagging (#1563)

When a procedure or ordering is compressed into memory, tag the **scope it applies to**. Compression discards contextual boundaries first, so an ordering that governs one sub-stage gets read as the ordering of the whole pipeline. A parenthetical is enough — and stating what the summary does *not* cover removes the ambiguity entirely.

| Anti-pattern | Required |
|--------------|----------|
| `release branch first → version bump → PR` (untagged → misread as whole-pipeline ordering) | `Ordering within the release stage: release branch first → version bump → PR (implementation commits go straight to develop)` |

Origin: #1563 찐빠 #5 — that exact summary described the ordering *inside* the release stage but was read as the ordering of the entire pipeline. Cross-ref: [[r013]] (Compact Output — be aware of what compression discards), Mid-Session Immediate Save above (preserving trigger context).

## Safety-Related Feedback Memory Framing

> Origin: #1307 — a delegation prompt framed a learning as "conclude it's a false positive and proceed," tripping the memory-poisoning safety classifier.

Safety-related feedback memories MUST use **verification-obligation form** ("this pattern triggers a duty to verify X; proceed only if verified, else STOP") — never **conclusion form** ("ignore the warning, it's a false positive"). Conclusion-form framing risks future sessions dismissing genuine threat warnings as memory-poisoning noise; writing triggers + STOP conditions instead preserves the warning's fail-safe intent.

## Session-End Retrospective Feedback (Model-Drafted)

Since `omcustom-feedback` is model-invocable (#1227), at session end the model MAY draft a retrospective feedback issue summarizing notable session friction or learnings — instead of only prompting the user to file it manually.

**Trigger conditions**: session-end detected AND notable friction/learning observed AND `omcustom-feedback` skill active.

**Key constraint**: The model NEVER auto-submits. Every draft passes through the skill's Phase 4A preview + confirmation gate before any GitHub issue is created. The user approves before publication.

| Path | Who Drafts | Who Approves |
|------|-----------|-------------|
| Manual (existing) | User | User (self-review) |
| Model-drafted (new) | Model | User via Phase 4A gate |

This complements — does not replace — the existing self-check item "prompt user to trigger omcustom-feedback". The Session-End Self-Check wording was updated to reflect that the model MAY draft instead of only prompting.

See [[omcustom-feedback]] for Phase 4A gate details.

## Platform Notes (v2.1.228/232+)

**Session cleanup was deleting project memory folder contents (fixed v2.1.228+).** On older CC, MEMORY.md and archive files could be lost during the session-cleanup step. Diagnostic consequence: a missing memory entry is not necessarily a *write* failure under the Enforcement section's failure policy below — the write may have succeeded and cleanup may have removed it. Per the Memory Scopes table above, the `project` scope (`.claude/agent-memory/`) is git-tracked and therefore recoverable; `user` and `local` scopes have no recovery path.

**Cowork sessions do not inline external @-imports in user-scope memory (v2.1.232+).** If a `~/.claude/agent-memory/` MEMORY.md pulls content in via `@`-import, that content may be absent from the context depending on session kind. Anything that must always be loaded belongs in the **body** of MEMORY.md rather than behind an import reference — consistent with the Attention-Weight Tiering rule of keeping Hot/Warm content inside the 200-line budget.

## Enforcement

Prompt-based + Stop hook (soft block for session-end saves) per [[r021]]. Memory write failure remains non-blocking; **v2.1.210+** changed the failure mode — a write that pushes MEMORY.md past the read-limit budget now returns an explicit error instead of silently truncating, so recovery means reducing via Attention-Weight Tiering (archive Cold entries) before retry, not assuming truncation absorbed the overflow. (This version note was retired to an HTML comment in the source at v1.1.45 under the [[r016]] v2.1.212 retention floor — the oversize-write recovery behavior it describes is unchanged, only its auto-injection cost was removed.)
