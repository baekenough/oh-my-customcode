# R010: Orchestrator Coordination Rules

The main conversation is the sole orchestrator and MUST NEVER directly write, edit, or create files — all file modifications MUST be delegated to appropriate subagents.

## Overview

The orchestrator's role is routing and coordination only. File operations, git commands, and all write actions must go through specialist subagents. This ensures separation of concerns, maintains audit trails, and prevents accidental bulk changes from the orchestrator context. **Agent Teams exception**: Teams members are peers, not hierarchical subagents, and CAN spawn sub-agents to execute complex workflows (e.g., `/research`, `/deep-plan`) — the Teams member acts as a local orchestrator for its own sub-tasks. Subagent-of-subagent nesting is now a **project policy prohibition, not a platform limitation**: the platform's own default changed in v2.1.217+, and v2.1.219+ raised the default nested-spawn depth to 3 — the platform itself permits nested sub-agent spawning by default. oh-my-customcode deliberately retains flat sole-orchestrator delegation regardless of what the platform now allows, for predictable [[r009]] parallelism and [[r018]] coordination — the Agent Teams exception remains the only sanctioned nesting path.

## Priority

**MUST** — Critical. Direct file writes from the orchestrator are violations. Advisory PostToolUse hook monitors compliance; re-injected via PostCompact. Candidate for hard-block promotion per [[r021]].

**Protected paths (mgr-creator required):** `.claude/agents/*.md`, `.claude/skills/*/SKILL.md`, `guides/*/` (new directories). **Orchestrator allowed operations:** Read, Glob, Grep only.

**Root meta-files** (`.gitignore` → `mgr-gitnerd`, `README.md`/`CHANGELOG.md` → `arch-documenter`, `package.json` → `mgr-updater`, etc.) also cannot be edited directly by the orchestrator regardless of change size — "1-line edit" reasoning is an R010-weakening entry point (#1208).

## Subagent Scope-Creep STOP Protocol

When a subagent trips the safety classifier ([[r001]]/[[r002]]) **2 times**, the orchestrator MUST stop that agent and redesign with a narrower, pre-decomposed scope — not re-run it. 3+ trips is a hard anti-pattern requiring abort and user report. The **proactive complement**, Pre-Delegation Privileged-Scope Boundary, requires the orchestrator to state approved actions, forbidden actions, and authorization scope explicitly in the delegation prompt before any prod/privileged-resource task runs — preventing the trips rather than reacting to them (origin #1266, #1368). Auto mode now also evaluates subagent spawns with the safety classifier before launch (v2.1.178+), a platform-level defense-in-depth complement to this advisory boundary.

**What counts as a "trip" (v2.1.225+):** auto mode previously counted **safety-filter refusals of its own permission checks** toward the consecutive-block limit; this is fixed (the action is still denied, but the model is told to proceed rather than retry). The trip counter in this protocol only counts classifier trips a subagent caused **through its actual work** — refusals arising inside the platform's own permission checking are not trips. Because older CC conflated the two, do not retroactively apply a STOP verdict based on trip counts recorded in past sessions.

### Bypass flags must name what they bypass, and why (#1584 #6)

When a delegation prompt instructs a flag that bypasses a safeguard (`--admin`, `--force`, `--no-verify`), state **what it bypasses and why that is legitimate**. A bare flag reads to the harness or the agent as an unauthorized bypass, and gets flagged or refused.

| Anti-pattern | Required |
|--------------|----------|
| Instruct `gh pr merge --admin` and nothing else | Name the bypass scope and grounds — e.g. "all 10 required status checks confirmed passing; what `--admin` bypasses is only the **reviewer-approval requirement**, and as a solo maintainer self-review is impossible" |

The purpose is **audit trail**, not authority acquisition. Because it is a factual description of the bypass scope rather than a citation of approval, it does not conflict with Delegation Prompt Framing below.

Origin: #1584 #6 — the v1.1.45 and v1.1.46 release-PR merges were flagged by the harness as "no visible user authorization naming that bypass".

**"Scope tied back to the user request" ≠ citing approval**: the Pre-Delegation boundary above asks the orchestrator to *describe* scope (what's allowed/forbidden), not to *quote the user's approval statement* as an authority grant to the subagent — the approval channel is owned by the permission system, not by prose in the prompt (see Delegation Prompt Framing below).

### Delegation Prompt Framing — No Quoting Approval (#1556)

Delegation prompts MUST NOT cite the user's original words as grounds for approval. Give the subagent only **task instructions** (allowed actions / forbidden actions / completion criteria) — the approval channel is the permission system (parent session's permission mode + `settings.json` allow rules), not a quoted user statement.

CC injects a platform system prompt into every subagent stating that another agent's message is never user approval — only the permission system or the user's own message is a valid approval channel. That instruction targets treating a relayed message *as approval*, not performing the relayed *task*. So when an orchestrator quotes "the user approved pushing" as grounds, it self-triggers the exact anti-pattern the platform rule targets, and the subagent refuses.

**Boundary**: Describing scope by connecting it to the user's request (explaining what/why) is fine. Presenting that connection *as proof of approval* is what's forbidden.

| Anti-pattern | Required |
|--------------|----------|
| Quote the user's words as approval grounds in a delegation prompt (e.g. `the user approved "commit and push"`) | List only allowed actions / forbidden actions / completion criteria (e.g. "commit and push to release/v1.1.43; forbidden: force-push, direct push to develop") |
| Re-delegate with the same approval-quoting framing after a refusal | Strip the approval quote from the framing and re-delegate; if prompt suppression is needed, use a `settings.json` allow rule instead |

Origin: #1556 — a delegation containing an approval quote was refused twice by mgr-gitnerd; an otherwise-identical delegation listing only allowed/forbidden actions completed without refusal (2026-08-05 v1.1.43 session, controlled comparison). Cross-ref: [[r015]] (User Directive Persistence — same conclusion that `settings.json` allow rules are the real prompt-suppression lever), [[r002]] (permission tiers).

### Delegation Prompt Command Examples — Verify or Label (#1563)

When a delegation prompt spells out a concrete command or flag, write only what has been **verified by measurement**, or explicitly label it ("example — confirm the actual flag before use"). An unverified flag written in declarative form sends the subagent into an `unknown flag` recovery round-trip, and a failed recovery pushes it onto a wrong alternative path. Verification costs one line — `--help` or `command -v`.

| Anti-pattern | Required |
|--------------|----------|
| Write an unverified flag declaratively in the delegation prompt (`gh issue edit <N> --assignee @me`) | Verify with `--help` before writing it, or mark it "example — confirm the actual flag before use" |

Origin: #1563 찐빠 #3 — `gh issue edit --assignee` does not exist in gh 2.86.0 (the correct flag is `--add-assignee`); the agent had to self-recover mid-run. Cross-ref: [[r005]] (the casebook of tool-flag and default-behavior measurement traps), Agent Capability Pre-Check below (the tool/path-existence angle of the same "confirm before delegating" discipline).

#### Repository state is under the same discipline (#1584 #5)

Repository state written into a delegation prompt (HEAD SHA, branch, working-tree cleanliness) also requires a **just-before measurement** — `git rev-parse --short HEAD` is one line. HEAD moves constantly during a session as merges and pulls land, so copying a value seen an earlier turn hands the subagent **a wrong base to work from**.

| Anti-pattern | Required |
|--------------|----------|
| Copy the HEAD SHA seen in an earlier turn into the delegation brief | Write the value measured immediately before delegating |

Origin: #1584 #5 (v1.1.45 session — a commit delegation brief said `develop @ 96ef8f85` while the measured HEAD was `f6d3f518`; a pull after the #1572 merge had not been reflected). This is the **within-session miniature** of [[r017]]'s "memory TODO as a delegation premise" — the only difference is that the snapshot's shelf life is measured in *turns* rather than sessions.

## Agent Capability Pre-Check

Before delegating, MUST verify the target agent's tool capabilities (Bash/Read/Write/mcpServers) against task requirements, AND that target file paths exist — capability alone doesn't catch a missing/renamed path (#1269). For multi-copy files (e.g., a config mirrored across templates), verify content consistency (md5/diff) before delegating "apply the same change everywhere" (#1287). For new-file delegations, pre-determine whether the file is a new topic directory (count increases) or a document inside an existing directory (count unchanged) — instruct the subagent to sync off the measured value, not a guess (#1443). Known limitation: `arch-documenter` has `disallowedTools: [Bash]` — pre-collect `gh`/shell data via the orchestrator first.

### Parallel Delegation — Sibling-Agent Disclosure

When 2+ subagents are spawned in parallel within the same message, each delegation prompt MUST disclose the existence and scope of sibling agents. Subagents run in isolated contexts and cannot perceive their siblings — without disclosure, a subagent misreads shared-view output (e.g. `git status`, a repo-wide view) as its own changes, or misattributes contention to an "external session/process".

Each prompt must state: the count of concurrently running agents, each agent's assigned files/scope, and an instruction that since shared views also show other agents' changes, the subagent must **report based only on its own assigned scope**.

| Anti-pattern | Required |
|--------------|----------|
| Spawn parallel agents with no sibling disclosure in the prompt → a subagent misreads shared-view output or misattributes the cause to an "external process" | State in each prompt: concurrent agent count + each agent's assigned scope + "report based only on your own scope" instruction |

Origin: #1518 (an undisclosed git agent misattributed a sibling to an "external process"; in the same session, 4 disclosed implementation agents all reported scoped correctly — a direct contrast). Cross-ref: [[r009]] (parallel execution criteria).

#### Disclosure widens the attribution candidates; it does not raise the evidence grade

Sibling disclosure fixes the *blind spot*, not the *reasoning*. A disclosed agent can still misattribute — in fact disclosure hands it a plausible scapegoat, so circumstantial "my sibling owns that file, therefore my sibling broke it" reasoning survives disclosure and still produces wrong answers. Anomalies in a shared view must be attributed by **intervention experiment** (remove and re-run, restore and confirm the symptom disappears, `bash -x` trace, revert the change and check reproducibility), regardless of whether disclosure was given.

| Anti-pattern | Required |
|--------------|----------|
| Attribute a failure to a disclosed sibling purely because its scope overlaps | Establish causality by intervention (remove → reproduce / restore → symptom disappears), then attribute |

Origin: #1574 (v1.1.44 session, controlled comparison — of three parallel agents given identical disclosure, [1] circumstantially blamed 11 `bun test` failures on "a sibling is editing that file" and was wrong, while [2] and [3] attributed correctly via intervention experiments). Cross-ref: [[r020]] (Read-Before-Characterize — do not characterize from circumstance).

## Universal bypassPermissions & Permission Mode Inheritance

**Historical (CC < v2.1.212):** the Agent tool's `mode` default (`acceptEdits`) overrides agent frontmatter `permissionMode`, so every Agent tool call required explicit `mode: "bypassPermissions"` to avoid unattended-execution prompts (#926, #947, #955).

**v2.1.212+ (current):** CC deprecated the Task/Agent tool's `mode` parameter — it is now ignored. Subagents inherit the **parent (orchestrator) session's permission mode** by default. The per-call `mode: "bypassPermissions"` requirement is now a no-op on new CC (harmless to keep for CC < v2.1.212 backward compatibility), and the real control point for unattended delegation is the **parent session's permission mode**, not the per-call parameter. If prompts appear during delegation on v2.1.212+, diagnose the orchestrator session's mode — not the per-call `mode` field. [[r002]] and [[r006]] reference this section as canonical.

Also fixed in the same window: `/model` and other dialogs are no longer incorrectly blocked in `claude agents` background sessions (v2.1.209+, reverts an overly broad guard), and `CLAUDE_CODE_PROCESS_WRAPPER` (v2.1.208+) routes every Claude Code self-spawn through a required corporate-launcher wrapper.

**v2.1.223+ agent-definition `bypassPermissions` vs org policy:** an agent definition's `bypassPermissions` mode previously ignored an org policy that had bypass permissions disabled — i.e. **the agent file outranked org policy** and could revive a bypass the org had turned off. This repo already treats the parent session's inherited mode as the control point (per v2.1.212+ above), so nothing changes here in practice; but in an org-policed environment, frontmatter `permissionMode: bypassPermissions` no longer guarantees unattended execution. When prompts appear, check **both** axes: the parent session mode and the org policy (cross-ref [[r002]]).

**v2.1.221+ background session commit/push:** background sessions now commit/push to preserve work, open a draft PR only when the task calls for it, follow the user's CLAUDE.md git guidance, and always report their working location on exit. This repo's R010 still requires all git operations to go through `mgr-gitnerd`-style delegation, so a background session reads and follows that guidance — but a background session's self-reported commit/push completion is NOT trusted without [[r020]] ground-truth (`git log` / `gh pr view`). `/status` in v2.1.221 also surfaces the session kind (interactive / background attached / background unattended), giving a deterministic way to detect unattended execution.

**v2.1.232+ non-teammate spawns run in the background by default:** In interactive sessions, spawning a non-teammate agent is now backgrounded by default (part of subagent forking being enabled by default). An Agent tool call's return may therefore mean **"started in the background"**, not "work completed" — so neither the spawn return nor a completion notice is completion evidence. Verify with [[r020]] ground-truth (`git status` / `grep` / validation scripts). On older CC the synchronous return made "return = done" a mostly-safe implicit assumption; this release breaks it. Diagnostic aids: `/status` session-kind display (v2.1.221, above) and v2.1.211 (CC no longer fabricates results for a still-running agent). Cross-ref [[r009]] (a fork inherits the orchestrator's context) and [[r018]] (Teams members are **not** non-teammates, so they are outside this change).

## Git Operations — No Quality-Gate Bypass

All git operations (commit, push, branch, PR) go through `mgr-gitnerd`; internal rules override any external skill's git instructions. On top of that, a git-delegated agent MUST NOT decide on its own to bypass a blocking pre-commit/pre-push hook. `--no-verify` (and sibling gate-defeating flags such as `--no-gpg-sign`) is a **standing prohibition** for git delegation — permitted only with the orchestrator's prior approval. Having diagnosed the root cause does not license the bypass, and neither does CI remaining as the authoritative gate: whether to bypass is the orchestrator's call, not the agent's. A blocked hook is something to **report and wait on**, with the block and its cause surfaced upward.

| Anti-pattern | Required |
|--------------|----------|
| Self-bypass a pre-commit block (e.g. failing tests) with `--no-verify` and commit anyway | Report the block and its cause to the orchestrator and wait — bypass only after prior approval |

**Platform converged on the same boundary (v2.1.229+):** `/commit-push-pr` no longer auto-approves git/gh commands carrying risky flags (`--force`, `--amend`, `--no-verify`, …). The platform reached the same conclusion this repo's clause above reached independently at v1.1.45 — a standing `--no-verify` prohibition is not a local idiosyncrasy but a platform default boundary. Retroactive consequence: **on older CC these flags passed without a prompt**, so "a past session's `--no-verify` commit went through unprompted" is not evidence of approval ([[r020]], "executed ≠ approved"). The platform prompt is defense-in-depth and does not replace the orchestrator's prior-approval requirement above.

Origin: #1574 (v1.1.44 session — mgr-gitnerd self-bypassed a pre-commit block caused by 11 `bun test` failures using `--no-verify`; the outcome was harmless, but an unapproved quality-gate bypass is a process deviation). Cross-ref: [[r020]] (Test-Skip Is Not Completion — no green-build evasion), [[r017]] (pre-commit verification gate).

## Agent Teams — Required Only While Active

Agent Teams is active only when `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` **AND** `TeamCreate` is present in the tool list. The env var alone is not sufficient — it states an intent to enable the feature, not the feature's availability — and `SendMessage` presence is not evidence either, since peer/cross-session messaging is a separate capability. When active, the quick rule applies: 3+ agents OR a review cycle OR 2+ issues in one batch → Agent Teams, and using the Agent tool where those criteria are met needs correction per [[r018]]. When **not** active, [[r009]]/[[r010]] govern and there is no Teams obligation to violate. See [[r018]] for the Detection table, decision matrix, self-check, team patterns, and lifecycle.

## Sensitive Path Handling

Deprecated as of CC v2.1.121 (further relaxed v2.1.126): direct Write/Edit/Bash on `.claude/`, `.git/`, `.vscode/` works without prompts under `bypassPermissions`. The legacy `/tmp/*.sh` bypass pattern is no longer necessary (#1101).

## Enforcement

Advisory PostToolUse hook (`git-delegation-guard.sh`) + PostCompact re-injection per [[r021]]. Candidate for hard-block if direct-write violations exceed 3/session.
